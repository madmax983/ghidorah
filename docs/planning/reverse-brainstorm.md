# Planning record: reverse brainstorm

- Date: 2026-10-16.
- Status: planning input. This file records failure modes and their guards. It does not record decisions. The blue hat section of [six-hats.md](six-hats.md) records the decisions.
- Evidence base: [docs/research.md](../research.md). A reference such as "research 3.4" points to a section of that file.
- Related records: [brainstorm.md](brainstorm.md) (ideas) and [six-hats.md](six-hats.md) (evaluation and decisions).

## Method

- Technique: reverse brainstorming. First ask "How can we make ghidorah fail?". Then invert each failure into a requirement. Then attach a test or a guard that detects the failure.
- Each row has a stable ID (`FM-01` to `FM-56`) and a category.
- The "Symptom" column gives what an agent sees when the failure happens. The eval harness can count each symptom (see key insight 10).
- Some guards in this file differ from ideas in [brainstorm.md](brainstorm.md). Examples: the transaction default of `batch_run` (FM-53) and the cursor staleness rule (FM-06). The six hats compare them, and the blue hat lists the open items.

| FM-01 | AGENT | Token flood | Return whole collections and whole bundles. `func_list` on a 40k-function binary, or `func_get include=[disasm,decomp,xrefs,callers]` on a 20k-instruction function, sends megabytes. | FM-05 | AGENT | Number and address traps | Send addresses as JSON numbers, so `0xffffffff81000123` loses its low bits in JS or Python floats. ## Key insights

1. **Highest-leverage guard.** Put the cross-cutting agent guards in the registry dispatcher, not in each handler. These guards are the output budget, the result envelope, argument coercion, rev and partial stamping, error codes and panic isolation. Then one `registry_matrix` test (every tool x every example x every fixture x every profile) proves FM-01, 02, 05, 09, 10, 11, 17, 34 and 49 together. Build this test first.
2. **Determinism comes before almost every other guard.** Golden files, MCP transcripts, eval baselines and prompt caching all need byte-identical output. Two guards are day-1 gates: clippy `disallowed-types` (HashMap and HashSet) and the two-process byte-equality test (FM-03).
3. **Hostile input causes four separate resource failures, and each one needs its own guard.** Panics: `catch_unwind` plus lints. Memory: clamp before allocation, plus a counting allocator in tests. Time: a `Fuel` type in every loop and worklist, plus a step watchdog. Stack: iterative graph algorithms, depth counters and a fixed-stack worker thread. `catch_unwind` covers only panics. An OOM or a stack overflow stops the whole MCP server and loses all state that was not persisted. This is why FM-07 and FM-36 need an fsync per commit.
4. **Oracle strategy.** `xtask golden` makes the goldens once with external tools (objdump, llvm-mc, readelf, gcc and clang), from first-party C fixtures that have no license problem. Check in the binaries and goldens with SHA-256 headers, so plain `cargo test` stays hermetic. Use cheap internal oracles every run: cross-view consistency, CFG invariants, structurer trace equivalence, exhaustive fusion, pagination conservation and undo/redo state hashes. These find most bugs with no external tool.
5. **Composition layer (gap 3.11).** Make `batch_run` one registry tool. Steps are `{id, tool, args}`. `$ref` paths point into earlier step results. `for_each` is capped. There is no nesting and no conditionals or loops. Fuel and output budgets are shared, and a `resume` token continues a stopped batch. `atomic` is optional, a step reads earlier writes, and annotations come from the steps. Prefer this to a query language or a Hex-Rays-style code mode. It reuses the schemas, IDs, errors and budgets, it stays deterministic, and it needs no interpreter. A Python interpreter would break the zero-dependency rule.
6. **Eval harness (gap 3.11).** Run it offline, with no LLM, in `cargo test`. Tasks have gold answers and reference traces. Metrics are calls, output characters, errors, correctness and determinism, with a 10% regression gate against a checked-in baseline. A scripted naive agent that follows only `hint`, `valid_example`, `candidates` and `next_cursor` measures error recoverability, and the target is 100%. Add `tool_search` recall, plus record and replay of real sessions as regression traces. This harness also settles the open question "JSON or compact text by default" with a measurement.
7. **Process guards that need no external tools.** (1) No `source` key in `Cargo.lock`, plus `[net] offline = true`. (2) SHA-256 hashes of the verified sources in `verify/results.json`, which detect proof drift without Verus in CI. (3) `mutants-lite` with about 40 curated mutants, which proves that the tests catch real bugs. (4) Golden headers with fixture hashes, which stop silent re-blessing. (5) A hermetic run with a reduced PATH.
8. **Decisions that these failure modes force (record them as ADRs).** No implicit active program, so every call takes `binary_id`. Any commit invalidates cursors. A digits-only address string is decimal, with did_you_mean for the hex reading. JSON rejects lone surrogates. The provenance lattice is DEFAULT < ANALYSIS < AGENT < IMPORTED < USER, and an agent overwrite of IMPORTED needs a recorded `force`. Analysis is single-threaded, and the server uses std reader, worker and writer threads. Error enums are hand-written. Unsafe code exists only in dev-only oracle and test crates. (The six hats review these proposals. Some of them are still open. See the blue hat in [six-hats.md](six-hats.md).)
9. **Delivery.** The `e2e_elf_x86_64` transcript test exists as RED on day 1, and `xtask budget` tracks a per-crate line budget. Suggested budget, about 33-35k production lines: core (addr, AddressSet, IDs, Limits, SHA-256) 1.5k, json 1k, loader-elf 3k, x86 decoder and printer 5k, IR, lifter and flags 4k, analysis 4.5k, decompiler 4k, program, tx, journal and provenance 2.5k, tools, registry and batch_run 4k, mcp and cli 1.5k, Tier-0 prototypes and noreturn data 0.5k, eval 1.2k, xtask 1.2k. testkit (0.6k) is dev-only. Defer explicitly: PE, Mach-O, AArch64, RV64, the Itanium and MSVC demanglers (keep the Rust v0 demangler only if the budget allows), the full C parser and the prototype DB tiers 1-3, BSim and VT, sancov fuzzing, Streamable HTTP, overlays, and MCP resources and prompts beyond a minimal set.
10. **Every failure mode has an observable agent symptom** (repeated calls, truncation notices, contradictory answers, timeouts). Each symptom is a metric that the eval harness can count. The harness therefore closes the loop between the reverse-brainstorm list and regression detection.
